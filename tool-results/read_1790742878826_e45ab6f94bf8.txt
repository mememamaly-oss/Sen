    69→## What v3.0.0 adds (Phase 58 — Business-Logic / Workflow Intelligence)
    70→
    71→Every scanner before v3.0.0 — SENTINEL included — reasons about REQUESTS: one
    72→endpoint, one parameter, one response. But the most expensive vulnerabilities
    73→in real applications live in PROCESSES: the ordered, stateful sequences an
    74→application uses to do actual work (login -> select account -> enter amount ->
    75→create transfer -> confirm). A per-parameter scanner is structurally blind to
    76→them because the defect is not IN any single request — it is in the RELATIONS
    77→between requests: the order, the one-shot-ness, the binding of approved values,
    78→the role boundary of a step. v3.0.0 gives SENTINEL that process-level frame of
    79→reference. The engine (sentinel/workflow.py):
    80→
    81→LEARN (--workflow, safe): clusters discovered surfaces into flow directories,
    82→finds the anchor (a GET page carrying an in-cluster form) and performs a GUIDED
    83→WALK — following the chain the application itself lays out (each landing page
    84→carries the next form), including steps a crawler can never see because they
    85→live behind POST landings. The walk learns, with bounded budgets and canary
    86→values only: the step chain, the RESOURCE LINKAGE (the object ids one step
    87→mints and a later step consumes — e.g. tid), the STATE ORACLE (the page that
    88→echoes those ids), and the EXECUTION MARKER vocabulary (the word-level delta
    89→of a resource's oracle line across the final step — e.g. PENDING -> EXECUTED).
    90→The learned flow model rides the Application Map: entry, steps, resource
    91→params, oracle, markers, declared-privilege options.
    92→
    93→ATTACK (--logic-active, explicit opt-in, loud warning): the five business-
    94→logic invariants a human pentester tests — and a parameter scanner cannot:
    95→
    96→  1. business_logic_step_bypass           — create without its mandatory
    97→                                            predecessor (draft never required)
    98→  2. business_logic_out_of_order          — the FINAL step executes a resource
    99→                                            that was never created (implicit
   100→                                            creation from POSTed params)
   101→  3. business_logic_value_tamper          — an approved value (amount) is
   102→                                            REPLACED at execution time
   103→  4. business_logic_duplicate_execution   — replaying the final step executes
   104→                                            the operation again (no idempotency)
   105→  5. business_logic_privilege_escalation  — an option the UI itself labels
   106→                                            "admin only" is executed by a
   107→                                            lower-privilege session
   108→
   109→THE PROOF DOCTRINE (VR-20): a manipulation is reported ONLY when the state
   110→oracle PROVES the outcome — a new canary-bearing object, a second execution of
   111→the same resource, or an executed line carrying the tampered canary. A server
   112→that merely fails to reject is NEVER a finding; the disallowed thing must
   113→actually happen. Unprovable manipulations (no oracle, no marker, no second
   114→role, option broken for everyone) are skipped loudly in the stats, never
   115→guessed. Every attack runs on a FRESH isolated session with canary values;
   116→login/logout-shaped surfaces are never submitted; budgets are bounded per
   117→flow.
   118→
   119→Ground truth v9 (64 rows — 35 TP / 29 TN): fixture v8 adds the five-step
   120→transfer wizard /wf/transfer/* (vulnerable to all five classes) and its
   121→hardened twin /wf/safe/transfer/* (every manipulation refused with the right
   122→status and NO state change — the per-session ledger is the oracle that proves
   123→it either way). The benchmark arms the full battery: 5/5 verified on the
   124→vulnerable wizard, 5/5 honest no_proof on the twin, ZERO false positives.

   161→## What v2.9.0 adds (Phase 57 — the Credential Vault)
   162→
   163→Authorized security tests FIND credentials — a leaked AWS key in a debug
   164→endpoint, a hard-coded token in a config document. v2.8.0 answered that the
   165→only safe way available to it: detect, mask, DISCARD the raw value. v2.9.0
   166→does what a professional engagement actually needs: retain the evidence
   167→ENCRYPTED, release it only to the organization owner, prove every access,
   168→and shred it after delivery. The nine confirmed specifications, all
   169→implemented and gate-verified:
   170→
   171→1. ENCRYPTED STORAGE — pure-stdlib authenticated encryption: ChaCha20
   172→   (RFC 8439, implemented from the spec) in encrypt-then-MAC composition with
   173→   HMAC-SHA256; enc/mac/wrap subkeys derived domain-separated from a 256-bit
   174→   blob key. The vault FILE never contains a plaintext secret — byte-level
   175→   gates in the test suite prove it (data.count(raw) == 0).
   176→2. AUTHORIZED KEYS ONLY — access is granted to KEY FILES (32 random bytes,
   177→   0600, deterministic key_id), never to passwords in code or Git. The vault
   178→   holds one encrypted wrap of the blob key per authorized key.
   179→3. AUDIT TRAIL — every operation (INIT/AUTHORIZE/REVOKE/STORE/LIST/EXPORT/
   180→   REPORT/PURGE) appends {ts, actor=key_id, action, target} INSIDE the
   181→   encrypted blob: confidential and tamper-evident.
   182→4. MASKED EVERYWHERE — records carry a non-reversible preview (4-char prefix
   183→   + length). list()/status and every public artifact show previews only;
   184→   scrub() walks whole report structures replacing known raws with ********
   185→   (defense in depth).
   186→5. AUTHENTICATED REVEAL — `sentinel vault report` / `export` are the ONLY
   187→   plaintext paths, both audit-logged first, both marked CONFIDENTIAL —
   188→   organization owner only.
   189→6. NO LEAKAGE CHANNELS — raw values never enter findings, events, logs,
   190→   terminal output, stats or any report artifact (gate-asserted byte-level).
   191→7. SHRED-AFTER-DELIVERY — purge rewrites the blob WITHOUT the value (fresh
   192→   nonce, new ciphertext); the audit entry survives so the destruction is
   193→   provable.
   194→8. ORG SEPARATION — one vault file per organization; the org id is bound
   195→   into the AEAD associated data, so a blob transplanted between vaults
   196→   fails its MAC (gate-asserted).
   197→9. KEYS OUT OF CODE/GIT — keygen creates 0600 key files to hand to an
   198→   authorized party; a shipped .gitignore-vault template covers vault, key
   199→   and reveal-report patterns; a revoked key triggers full blob-key rotation
   200→   (the removed key cannot open ANY copy of the file).
   201→

   261→## What v2.8.0 adds (Phase 56 — the Intelligence Layer)
   262→
   263→The question the platform answers grows from "is this input injectable" to
   264→"WHO can do WHAT, WHERE, with what reach and what proof". Six new engines,
   265→all pure stdlib, all deterministic, all budget-capped:
   266→
   267→1. **Multi-User Authorization Engine (authz.py)**
   268→   * IDOR / BOLA — a low-privilege session retrieving ANOTHER account's
   269→     private object: unique victim-marker oracle, listing-surface guard
   270→     (multiple markers = directory, not object access), admin-reads-user
   271→     plausibility exemption. VR-17 = fresh VICTIM object with the same
   272→     attacker.
   273→   * Vertical escalation — a low-privilege session receiving the privileged
   274→     view of an admin-only surface. Full access differential required:
   275→     anonymous gated (401/403/login-redirect), privileged 200, low-privilege
   276→     200 with the privileged BODY. VR-18 = fresh replay with the SAME
   277→     low-privilege session.
   278→   * Access matrix — role x endpoint statuses (gate status recorded, never
   279→     the followed-redirect landing) feeding the Application Map.
   280→   * Safety contract: GET-only replays, one cookie jar per account,
   281→     logout-shaped paths never replayed, deterministic ordering, budget caps.
   282→
   283→2. **Credential Exposure Engine (secrets.py)** — AWS access keys, GitHub
   284→   tokens, DB connection URIs. Raw values are NEVER stored: evidence carries
   285→   prefix+length masks only. VR = fresh fetch re-exposure.
   286→
   287→3. **Parameter Intelligence (paramintel.py)** — parameter kind
   288→   classification (numeric / search / filename / url / token /
   289→   json_object...), value-shape inference and upgrades, data-object
   290→   clustering; JSON-object batteries are provably skipped (skip reasons in
   291→   the ledger, not silent drops).
   292→
   293→4. **Coverage Ledger (coverage.py)** — the honest per-endpoint account:
   294→   passive / secrets / active / authz activity, skip reasons, coverage %,
   295→   discovered vs tested vs untested.
   296→
   297→5. **Application Map (appmap.py)** — surfaces (page / api / form_or_action /
   298→   static), authentication mode, roles tested, access matrix, data objects,
   299→   workflows.
   300→
   301→6. **Fingerprint + Impact (fingerprint.py, evidence.py)** — WAF named
   302→   signatures and tech platform map (headers/cookies/frameworks/AngularJS);
   303→   every verified finding carries an impact grade (proven / indicated), a
   304→   plain-language statement, the safe-proof note, and the full evidence

   366→## What v2.7.0 adds (Phase 55 — five new verified vulnerability classes)
   367→
   368→1. **SSTI — Server-Side Template Injection (DETECT-15, CRITICAL)**
   369→   Template-syntax arithmetic battery across the four dominant families
   370→   ({{ }} Jinja2/Twig, ${ } FreeMarker/EL, <%= %> ERB, #{ } Ruby/Thymeleaf).
   371→   Oracle: the COMPUTED result (49) appears in the response while the literal
   372→   expression does NOT — raw echo is reflection, never evaluation. VR-12
   373→   re-tests the winning syntax family with fresh operands ({{12*11}} -> 132):
   374→   ambient page numbers cannot reproduce a fresh computation.
   375→
   376→2. **CSRF — cross-origin acceptance (DETECT-16, MEDIUM)**
   377→   State-changing POST forms carrying NO anti-CSRF token are replayed with a
   378→   hostile Origin+Referer. The oracle is acceptance: the cross-origin request
   379→   must succeed like the same-origin baseline (same status, similar body).
   380→   Honesty gates: token-bearing forms skipped outright, read-only surfaces
   381→   (stock/search/login) skipped, 401/403-gated baselines skipped (no honest
   382→   anonymous oracle). VR-13 re-tests with a FRESH hostile origin.
   383→
   384→3. **NoSQL operator injection (DETECT-17, CRITICAL)**
   385→   JSON-body endpoints where a $-operator object ({"$ne": "x"}) flips a
   386→   REJECTED baseline into an ACCEPTANCE — the Mongo auth-bypass shape. Full
   387→   JSON bodies ride engine body_override. VR-14 re-tests with a DIFFERENT
   388→   operator ($gt after $ne).
   389→
   390→4. **JWT unsigned-issuance analysis (DETECT-18, MEDIUM)**
   391→   Auth-shaped endpoints are replayed benignly; responses (body + Set-Cookie)
   392→   are mined for JWTs. An issued token with alg=none and an EMPTY signature is
   393→   a defect by RFC 8725 §3.1. Signed issuance (HS256/RS256) is normal and stays
   394→   silent. VR-15 = fresh replay must issue another none-token.
   395→
   396→5. **Host header injection (DETECT-19, MEDIUM)**
   397→   A canary Host header on GET HTML endpoints; reflection into the response
   398→   (Host-built absolute links — the reset-poisoning class) is the oracle.
   399→   VR-16 re-tests with a FRESH canary host.
