# عرض SENTINEL v4.0.0 التجريبي — 5 دقائق
## من "قائمة ثغرات" إلى "توأم رقمي أمني قابل للاختبار"

**الجمهور:** قادة تقنيون / مشترو أمن / مهندسون
**الرسالة الواحدة:** SENTINEL لا يفحص التطبيق فقط — يبني نموذجًا معرفيًا للتطبيق، يولّد فرضيات هجوم منه، ثم يثبت أو ينفي كل فرضية بدليل قابل لإعادة الإنتاج.

---

### الدقيقة 0–1: الفكرة (شاشة واحدة)

> "أدوات الفحص التقليدية تجيب: هل هذا المدخل قابل للحقن؟
> SENTINEL v4.0.0 يجيب: **من يستطيع فعل ماذا، في أي خطوة، بأي كائن — والدليل أمامك.**"

ارفع لوحة القيادة الزجاجية (`glass dashboard`):
```bash
python3 -m sentinel.cli report --db results/sentinel_v400_live.db \
        --format glass --out demo.html && open demo.html
```
**قل:** هذه ليست صفحة نتائج — هذا **التوأم الرقمي**: هويات، أدوار، أسطح، كيانات أعمال (Order/Transaction/Account)، سير عمل متعدد الخطوات، حالات، وكل نتيجة مربوطة بالسطح الذي أنتجها.

### الدقيقة 1–2: المحرك الاستنتاجي (العقل)

```bash
python3 -m sentinel.cli twin --db results/sentinel_v400_live.db
```
**اعرض** `stats.reasoning` من ملف الفحص:
- "النظام ولّد 31 فرضية هجوم **من أنماط الرسم البياني نفسها** — ليست قوائم endpoints مبرمجة مسبقًا"
- مثال حي من ginandjuice.shop: `R-TOKENLESS-WRITE` على POST /catalog/cart → اختبرها محرك CSRF → **verified** (فرضية تحولت لثغرة مثبتة)
- فرضية أُنفيت → محركها ركض والبرهان فشل → "refuted" وليس صمتًا
- فرضية لم تُختبر → **السبب مكتوب** ("requires_second_identity") — هذا إثبات تغطية الاستنتاج، ليس نقصًا

### الدقيقة 2–3: الدليل الحي (Evidence OS)

```bash
python3 -m sentinel.cli reproduce --db results/sentinel_v400_live.db \
        --finding F-d8bbff4e3e
```
**قل:** زر "إعادة إنتاج الثغرة" أصبح أمرًا واحدًا. كل نتيجة مؤكدة تحمل:
فرضية الهجوم ← الشروط المسبقة ← الطلبات ← الأدلة ← الهوية ← الحالة قبل/بعد ← الأثر ← وصفة إعادة الإنتاج خطوة بخطوة.
**لا يوجد "SQL Injection — High" ثم صمت.**

### الدقيقة 3–4: منطق الأعمال عبر الهويات (الأصعب في السوق)

```bash
python3 -m sentinel.cli benchmark --out demo_bench.json
```
**اعرض** مصفوفة الالتباس: 38 TP / **0 FP** / 0 FN / 35 TN — F1 = 1.000
**اشرح الثمانية أسئلة التي يطرحها المحرك على كل سير عمل:**
1. تخطي خطوة إلزامية (bypass)
2. تنفيذ خارج الترتيب (out-of-order)
3. تبديل قيمة معتمدة (tamper)
4. تنفيذ مزدوج / لا idempotency (duplicate)
5. خيار "admin only" ينفذه مستخدم (privilege)
6. **هوية ب تنفذ كائن أنشأته هوية أ (cross-user)**
7. **تنفيذ كائن من نوع آخر عبر سير عمل مختلف (cross-object)**
8. **تنفيذ كائن مُلغى عبر مسار التراجع (cross-state)**

**التوازن النزيه:** الـ fixture يحوي ثلاثة معالجات توأم — المصاب والآمن والمشترك — والمحرك أثبت الثمانية على المصاب، وصمت بصدق (no_proof) على الآمن. **صفر إيجابيات زائفة هي خاصية المنتج وليست حظًا.**

### الدقيقة 4–5: عقد الأمان + البوابة المؤسسية (Safe Attack Planner)

**اعرض** `stats.planner`:
> "كل عملية قبل تنفيذها مصنفة: قراءة فقط (تلقائي) / أثر منخفض بقيم canary (تلقائي) / تغيير حالة (يتطلب علمًا صريحًا --logic-active) / **تدميري (محجوب دائمًا)** — والقرار معلَّل بسؤال 'لماذا'. هذا ما يشتريه compliance."

```bash
python3 -m sentinel.cli report --db ... --format executive --ci; echo $?
# → ci_gate: FAIL/PASS + exit code للأنابيب (CI/CD)
```
اختم:
> SARIF 2.1.0 لكل فئة بقواعد مستقرة، تقرير تنفيذي بلغة الخطر التجاري، وذاكرة عبر الجلسات (نفس الثغرة تعود بعد نشر 'إصلاح' → recurring). **الأداة تحول فحصًا إلى أصل قابل للتدقيق.**

## أسئلة متوقعة وإجاباتها

| السؤال | الإجابة |
|---|---|
| هل يعتمد على LLM؟ | **لا.** نواة الاستنتاج deterministic بالكامل — نفس المدخلات تعطي نفس الفرضيات بنفس الترتيب. يمكن إضافة LLM محلي لاحقًا للتعبير/الترتيب فقط، لكن مسار القرار الأمني لا يعتمد عليه أبدًا. |
| كيف تمنعون الإيجابيات الزائفة؟ | قاعدة صارمة: **لا نتيجة بلا أثر مثبت** — oracle حالة ينقلب، أو canary ينفذ، أو ضحية تُقرأ من جلسة المهاجم. "الخادم لم يرفض" ليست ثغرة عندنا. |
| هل يكسر التطبيق؟ | بطاريات الهجوم خلف --logic-active بجلسات معزولة وقيم canary، والتدميري محجوب بالتصميم، وكل قرار مسجل. |
| ما الفرق عن Burp/OWASP ZAP؟ | هما request-level. نحن نضيف طبقة العملية: سير العمل، الهويات عبر الكائنات، آلة الحالة، والاستنتاج — وهي الطبقة التي تُخفي أغلى الثغرات (business logic). |
