## أحدث إصدار: v2.9.0 — Phase 57 (ذكاء الاعتمادات / Credential Vault)
- **خزنة الاعتمادات (Credential Vault)** بالمواصفات التسع المؤكدة:
  1. **تخزين مشفّر** — ChaCha20 (RFC 8439) + HMAC-SHA256 encrypt-then-MAC،
     بايثون قياسي خالص؛ ملف الخزنة لا يحوي أي نص صريح (بوابات بايت-مستوى)
  2. **وصول بمفاتيح مصرّح بها فقط** — ملفات مفاتيح 0600 (32 بايت عشوائية)،
     لا كلمات مرور في الكود أو Git
  3. **سجل تدقيق مشفّر** — كل عملية (INIT/STORE/LIST/EXPORT/REPORT/PURGE/
     AUTHORIZE/REVOKE) داخل النقطة المشفرة ذاتها: {زمن، فاعل=key_id، فعل}
  4. **تقنيع في كل مكان** — المعاينة غير القابلة للعكس (بادئة 4 + طول) في
     كل المخرجات العامة + scrub دفاعي يستبدل أي قيمة معروفة بـ ********
  5. **كشف بمصادقة** — `vault report` / `export` هما طريقا النص الصريح
     الوحيدان، مُدقّقان أولًا، موسومان CONFIDENTIAL لمالك المؤسسة فقط
  6. **لا قناة تسريب** — القيم الخام لا تدخل النتائج/الأحداث/السجلات/
     الطرفية/التقارير (مؤكد بايت-مستوى)
  7. **إتلاف بعد التسليم** — purge يعيد كتابة النقطة بدون القيمة (نونس
     جديد) ويبقي قيد التدقيق دليلًا على الإتلاف ذاته
  8. **عزل المؤسسات** — معرّف المؤسسة مقيد داخل AEAD: نقل نقطة بين خزنتين
     يفشل بـ MAC (مثبت)
  9. **مفاتيح خارج الكود/Git** — keygen + قالب `.gitignore-vault` + تدوير
     كامل لمفتاح الخزنة عند أي revoke (المفتاح الملغى لا يفتح أي نسخة)
- **عيب محرك اصطادته الواجهة الجديدة (ENG-11)**: `import secrets` في
  vault.py كان يحل لوحدتنا sentinel/secrets.py في وضع السكربت — أُصلح
  بمصدر عشوائية غير قابل للتظليل (os.urandom). ثالث عيب يصطاده البناء
  نفسه (بعد ENG-08 وENG-10)
- **التحقق الحي (testfire بـ Vault مسلّح)**: 673 طلبًا / 37 نقطة / **74
  مُتحقّق بها / 0 مرفوضة** (كل الأصناف السابقة سليمة) + **تعرض اعتمادات =
  0 — سالبة صادقة** مطابقة لخط الأساس + الخزنة مسلّحة وبقيت فارغة بأمانة
  + سجل التدقيق يوثق الدورة كاملة (INIT قبل أي طلب → LIST → AUTHORIZE
  لمالك المؤسسة — وملف المفتاح لا يُشحن مع المخرجات أبدًا)
- REST **بلا تغيير عمدًا**: خادم API لا يحمل مفاتيح، وتمرير مسارات مفاتيح
  عبر HTTP يخالف المواصفة 9 — الكشف عملية محلية بمصادقة ملف المفتاح
